「% 完了」に 50 と入力すると、スケジュールに何が起きるのか

行のなかでいちばん無害に見えるフィールドです。50 と入力するとバーが半分まで伸び、進捗会議では全員がうなずきます。ところが実績値を保存するスケジューリングツールでは、まったく無害ではありません。その一つの数字が、ほかのいくつかのフィールドを勝手に書き込みます。どれが書き換わるのかを知らないままだと、差異レポートはあなたの意図しない筋書きを語り始めます。

Ingantt for Web と Android では次のように動きます。

0 % を超えると実績開始日が入る

タスクの完了率が 0 % を超えた時点で、そのタスクは開始したことになります。そこで Ingantt は 実績開始日（Actual Start）を書き込みます。予定の開始日ではなく、実績です。実際には三日遅れて始まったタスクなのに、実績開始日を直さずに進捗だけ入力すると、スケジュールは「予定どおり始まって、進みが遅かった」と理解します。これは別の問題で、対処も別で、あなたの責任なのはそのうち一方だけです。

100 % で実績終了日が入る

タスクを 100 % にすると、Ingantt は 実績終了日（Actual Finish）を書き込みます。ベースラインとの比較が読むのはこのフィールドなので、速く済ませるより正しく入れる価値があります。

期間は裏で再計算される

実績期間（Actual Duration）と 残り期間（Remaining Duration）は、パーセントから再計算されます。10 日のタスクの半分なら、5 日終わって 5 日残り、という扱いです。あなたが別の申告をするまでは。作業が 50 % 済んでいても、残り半分に 5 日ではなく 9 日かかるのなら、正直な修正はパーセントではなく残り期間に入れるべきものです。パーセントは事実から出てくる結果であって、事実の代用品ではありません。

工数が連動するのは、そう指定したときだけ

実績作業時間（Actual Work）と 残り作業時間（Remaining Work）が「% 完了」から更新されるのは、プロジェクトオプション "Updating task status updates resource status" がオンのときだけです。ここが多くの人を驚かせる設定です。進捗は記録されているように見えるのに、工数もコストも動かず、理由が誰にも見えません。アーンドバリューの数字が固まったように見えるときは、まずこのスイッチを確認してください。

実務的にまとめると

  • 進捗は、既定の今日の日付ではなく、本当に意図している ステータス日 に対して入力する。
  • タスクの立ち上がりが遅れたときは 実績開始日 を直す。パーセントにその情報は載せられない。
  • 遅れは低いパーセントではなく 残り期間 に押し込む。
  • タスクの状況がリソースの状況を動かすべきかどうかは一度決め、あとは触らない。

Ingantt のヘルプセンターには、進捗の入力、実績列と残り列、そして最終的にこれらが流れ込む比較である ベースライン の詳細があります。
